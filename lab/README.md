# continuum-lab

Calibration notebooks. `fit.py` fits profile distributions from chain Parquet
tables; `grade.py` grades a devnet run against that fit; `explore.ipynb` wraps
both.

## Run

Needs Docker and the `mithril2pq-notebook:local` image.

```sh
make lab-image            # continuum-lab:local = notebook image + scipy + pytest
make lab-test             # pytest in the image, then go test ./lab/
make lab LAB_DATA=/path   # JupyterLab on :8888; LAB_DATA holds chain/ and export/
```

Data comes from two tools:

```sh
mithril2pq -mithril-archive preview -last-chunk 1500 -out chain
continuum run --fake --seed 7 --wallets 100 --epochs 2 --out run
continuum export run/events.log --out export
```

Fit, then grade (inside the image, from `/work/lab`):

```sh
python fit.py /data/chain --out /work/scratch/fit --name preview-fit
python grade.py /data/export --target /work/scratch/fit/target.json --out report.md
python grade.py /data/export --target ... --chain-dir /data/devnet-chain   # devnet chain tables
```

`fit.py` writes `profile.yaml` (parses with `profile.Parse`; guarded by
`profile_test.go`) and `target.json` (1001 quantiles per KS statistic, type
shares, fractions). `example/` holds the preview fit. `grade.py` exits 1 when
any statistic fails. Devnet chain tables come from
`mithril2pq -immutable-dir DIR -network-magic N`; on continuum's devnet a chunk
spans 50 slots, so pass `--slot-seconds` to match the slot length.

`tests/fixtures` is regenerated by `make_fixtures.py` (see its docstring): the
engine tables are a prefix of the seed-7 fake run, the chain tables are 100
preview transactions.

## Statistics

| name | meaning | test |
|---|---|---|
| outputs_per_tx, inputs_per_tx | spend inputs and non-collateral outputs of each valid tx | KS |
| log10_output_value | log10 lovelace per payment (an output that leaves the sender's unit, so change is excluded) | KS |
| activity_per_day | txs per day per sending unit, over units with at least one tx | KS |
| log10_gap_seconds | log10 seconds between consecutive txs of one unit | KS |
| tx_type_mix | share of plain, script (has script data hash), stake (stake certificates), pool (pool certificates) txs | total variation |
| address_reuse | share of outputs whose address already appeared on an earlier output | difference |
| change_to_sender | share of txs paying an output back to the sender address | difference |

A tx's sender is the address of its smallest spent-input source address.
Inputs whose source output lies outside the loaded range have no sender and
drop out of the per-address statistics only.

KS passes when the distance D is at most 0.1 (`--dmax`). That is an effect
size bound: at millions of samples the p-value rejects every real difference,
so it is reported but does not decide.

On the engine side actors stand in for addresses and the clock is
milliseconds. The engine only submits payments, so without devnet chain tables
`outputs_per_tx`, `inputs_per_tx` and `change_to_sender` are skipped, the type
mix is all plain and output value is the payment amount.

## Clusters and named profiles

`fit.py --clusters` turns one chain into a set of profiles:

```sh
python fit.py /data/chain --out /work/out --clusters --network preprod \
    [--window-days 90] [--seed 1] [--unit stake|address] [--weighting addresses|transactions] \
    [--kmin 2 --kmax 15] [--select elbow|min] [--max-units 100000] [--m2pq-version V]
```

1. The window is the last `--window-days` before the newest block with a
   transaction (or `--window-end-slot`), pinned in the output.
2. A unit is the stake credential of the sending address where it has one and
   the address otherwise (`--unit address` skips the credential).
3. Units that send mostly script calls (share of their txs at least 0.5) or
   staking certificates (at least 0.5) are split off as their own clusters.
   Shares of a unit with a few transactions sit exactly at 0 or 1, and a
   Gaussian mixture explains such pinned dimensions with tiny-variance
   components, so BIC never converged; script and staking use are categorical
   segments instead, and address reuse is left out of the mixture (it is still
   fitted per cluster as the `care` trait).
4. The remaining units get seven continuous features (`units.py`,
   `cluster.py`): tx/day, median gap, median payment value, inputs and outputs
   per tx, active days, longest dormancy, all log10-transformed and
   standardised.
5. A diagonal Gaussian mixture with k in `--kmin..--kmax` (default 2..15),
   `n_init=3`, `reg_covar=0.1` (a variance floor in standardised units),
   seeded. k is the BIC elbow (`--select elbow`, the default): the smallest k
   whose step to k+1 gains under 5% of the whole BIC drop across the range;
   `--select min` takes the minimum. The whole curve, the BIC-minimum k
   (`k_bic_min`) and whether it is interior to the range (`k_interior`) go in
   the header. At most `--max-units` units (a seeded sample) are used to fit;
   every unit is then assigned.
6. Each cluster is fitted like a one-profile run, from its units' statistics.

Cluster names use absolute thresholds in real units, from the median of the
cluster's units (shares are means), so a name means the same on every network:

| name | rule (first match) |
|---|---|
| `script-user` | at least 50% of the units' txs call scripts |
| `staker` | at least 50% are staking certificates |
| `frequent-trader` | median at least 1 tx per day |
| `occasional-payer` | median from 0.05 (one tx per 20 days) up to 1 tx per day |
| `holder` | median under 0.05 tx per day |

Clusters that share a name get a payment-size suffix from the median payment:
`-small` under 10 ADA, `-large` from 1,000 ADA, `-mid` between; any remaining
repeat gets `-2`, `-3` in cluster order. Names are therefore unique and fixed
by the seed. The thresholds are constants in `cluster.py`.

Output is `NETWORK.yaml` and `NETWORK.target.json`. The YAML header records
network, window, seed, k, BIC curve, unit, weighting, unit counts, and the
mithril2pq version and last chunk. `weight` is the cluster's share of units
(`--weighting addresses`) or of transactions (`--weighting transactions`).
`continuum run --profiles NAME` splits wallets by weight. The target holds the
overall statistics and each cluster's, so `grade.py` grades both.

Shipped files live in `../profiles/`. After refitting run `make
profiles-index`: it writes `profiles/index.json`, which maps each file's
profile hash (the one in a run's event-log header and export `run` table) to
its target, and `grade.py` uses it to pick the target when `--target` is
absent. `--scale k` changes rates but not the hash, so scaled runs grade
against the same target. `grade.py` reads each actor's profile from the run's
`store.db` (genesis actors have no Spawned record in the log); pass
`--store` when it is not beside the export directory.

Payment value is the output that leaves the sender's unit; change back to it
is not a payment.

## Mapping to the profile

| profile field | fitted from |
|---|---|
| `traits.competence` beta | per-unit share of txs with change back to the unit (method of moments, units with 3+ txs) |
| `traits.care` beta | per-unit share of outputs to previously seen addresses |
| `traits.patience` pareto | inter-tx gaps above their median (seconds) |
| `amount` | payment values: log-normal body up to the 90th percentile (truncated-likelihood fit) and a Pareto tail above it; `tail_share` is the share of payments above it, and the tail is left out when none is |
| `budget` | 20 times the tail scale, between 100 ADA and 1M ADA |
| `rates.base.send` | the 10th percentile of per-unit tx counts, as a rate over the active share of the window, divided by the chance a hodl wake-up is a payment (see `HODL_SEND_SCORE` in `fit.py`) |
| `rates.activity_tail` | Pareto index of per-unit tx counts above that percentile, at least 1.05 |
| `weights` | tx type mix: send, script_call, delegate, register_pool (the engine runs only send) |
| `hazards.dormancy` lognormal | gaps over one day (seconds) |
| `hazards.dormancy_onset` | the rate that leaves a unit active for its measured share of days, given the dormancy mean |

The engine's payments are floored at 2 ADA (`minPayment`), so chain outputs
below that are out of reach of the amount fit.

## Current results

Fit: Preprod, immutable chunks 0 to 6477 (7.79M txs), a 90-day window ending
at slot 139924767 (1.11M txs, 37,188 sending units), seed 1, stake-credential
units, weighting by units. The mixture is fitted on the 15,809 units that are
not script users or stakers. Its BIC curve falls from 253,299 at k = 2 to
142,478 at k = 15 with the steepest gains by k = 5 and a long shallow tail, so
the BIC minimum is at the top of the 2 to 15 range (not interior); the elbow
picks k = 5, and with the script-user and staker segments that is 7 clusters.
Real units are not Gaussian (payments pile on 2 ADA, counts are integers), so
the curve does not turn upward. Preview (chunks 0 to 29859, 8,529 units) is
the same fit: elbow k = 5, minimum at 15, 7 clusters.

| preprod cluster | share of units |
|---|---|
| script-user | 57.2% |
| occasional-payer-small | 25.0% |
| holder-mid | 6.1% |
| holder-small | 5.3% |
| occasional-payer-mid | 3.4% |
| holder-large | 2.7% |
| staker | 0.3% |

Grade: seed-7 fake run (`--profiles preprod`, 100 wallets, 2 epochs of
3,888,000 slots via `--epoch-slots 3888000`, 90 simulated days, 1,317
payments), overall:

| statistic | verdict | detail |
|---|---|---|
| outputs_per_tx, inputs_per_tx | skipped | no devnet chain tables |
| log10_output_value | FAIL | D=0.398, median 6.56 vs 6.30 |
| activity_per_day | FAIL | D=0.284, median 0.078 vs 0.200 per unit per day |
| log10_gap_seconds | FAIL | D=0.474, median 4.30 vs 2.72 |
| tx_type_mix | FAIL | TV=0.588; run is all plain, preprod 41% plain and 59% script |
| address_reuse | PASS | 0.924 vs 0.976 |
| change_to_sender | skipped | no devnet chain tables |

The first fit (Preview chunks 0 to 1500, one profile, a 20-minute run) failed
activity by three orders of magnitude (median 649 against 0.013 per day),
which was a short span and a rate fit that ignored dormancy and the hodl
agenda's 2% send score. Activity now lands within a factor of 2.6 of the
chain's median; the largest cluster (script-user) is the farthest off, with
56 actors giving 0.084 against 0.311. What is left:

- Payment value: the engine floors payments at 2 ADA, and the chain has many
  smaller outputs, so the low end cannot match. Clusters whose payments are
  exactly 2 ADA pass.
- Gaps: arrivals inside an active spell are exponential, the chain's are
  bursty, so engine gaps are longer.
- Type mix: the engine only sends payments.
- Clusters with a handful of actors (none for `staker`, three for
  `holder-large`) have too few samples for KS to mean much.
- Script users are 57% of preprod units and the engine cannot send script
  transactions, so their type-mix grade fails by construction.
